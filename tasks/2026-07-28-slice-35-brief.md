## Stage 3A — canonical mapping data file

Create `tools/ajami-pipeline/data/canonical-mapping.json` (or `.mjs` exporting a frozen object — your
choice, justify it). It is the single source of truth, consumed by everything else, never duplicated.

Required content, taken verbatim from the standard's Table A:

| Boko | Abstract token | Ajami | Unicode |
|---|---|---:|---:|
| `ɓ` | `B_GLOTTALIZED` | `ݑ` | `U+0751` |
| `ɗ` | `D_GLOTTALIZED` | `ط` | `U+0637` |
| `c` | `C_HAUSA` | `ث` | `U+062B` |
| `k` | `K_PLAIN` | `ک` | `U+06A9` |
| `ƙ` | `K_GLOTTALIZED` | `ࢼ` | `U+08BC` |
| `f` | `F_HAUSA` | `ࢻ` | `U+08BB` |
| `ts` | `TS_HAUSA` | `ڟ` | `U+069F` |
| `n` | `N_HAUSA` | `ࢽ` | `U+08BD` |
| `y` | `Y_PLAIN` | `ی` | `U+06CC` |
| `ƴ` + apostrophe-`y` aliases | `HAUSA_GLOTTALIZED_Y` | `ؿ` | `U+063F` |

Plus every remaining consonant from the standard's Table A (b, t, d, j, g, s, z, sh, m, w, r, l), the
provisional velar clusters (`kw`/`ky` → `U+0763`, `gw`/`gy` → `U+08C3`, `ƙw`/`ƙy` → `U+08C4`, all marked
`provisional`), and the vowel/combining-mark inventory from the standard's §7.

**`h` must NOT be one unconditional mapping.** Represent it as two tokens whose selection is deferred to
the classifier:
```
H_NATIVE_HAUSA   → ح U+062D
H_ARABIC_LEXICAL → ه U+0647
```

Also encode the `noncanonical_variant` set (Table B) and `forbidden_output` set (Table D) so the validator
can consume them later.

The table must be: centrally defined, deterministic, versioned (`orthography: "warsh_kano_ajamix_v1"`),
independently testable, and carry per-entry source/decision metadata (which of `[R12A]`/`[N4959]` supports
it, category `A`/`B`/`C` per the standard's §4).

**Every code point must be written as an explicit escape (`ݑ`) or hex string, never as a pasted
literal glyph** — pasted glyphs are how transcription errors enter, and this project has already had two.
Add a self-test asserting each entry's glyph matches its declared code point.

## Stage 3B — grapheme tokenizer

`tools/ajami-pipeline/tokenizer.mjs`. Operates on Hausa **graphemes and abstract units**, never isolated
JS characters.

Longest-match order, must include at minimum:
```
apostrophe+y   ƙw   ƙy   gw   gy   kw   ky   sh   ts   ɓ   ɗ   ƙ   ƴ
```

Requirements:
- `sh` must never decompose to `s`+`h`; `ts` never to `t`+`s`.
- **apostrophe-`y` must be recognized before generic apostrophe handling.**
- Uppercase/lowercase aliases converge on one token (`Ƴ`/`ƴ`, `'Y`/`'y`).
- Unicode composed and decomposed input normalized consistently (declare and apply NFC).
- Punctuation stays **outside** phoneme conversion — it must not be silently dropped either.

**Alias matching must be by code-point sequence, never by visible glyph.** The three apostrophes
(`U+0027`, `U+2019`, `U+02BC`) are visually near-identical; matching on appearance is a defect.

Emit tokenizer snapshots showing, per token: source substring, normalized form, token type, and
code-point sequence.

## Stage 3C — apostrophe classifier + full corpus audit (THE PRIORITY)

`tools/ajami-pipeline/apostrophe-classifier.mjs`. **Audit-first**: its job is to report and route, not to
convert aggressively.

Output categories:
```
GLOTTALIZED_Y   PAIRED_QUOTATION   GLOTTAL_BOUNDARY
MORPHEME_BOUNDARY   TYPOGRAPHIC_PUNCTUATION   AMBIGUOUS
```

**Only one rule is settled and may auto-resolve**: an apostrophe immediately forming the Nigerian Boko
`'y` consonant → `HAUSA_GLOTTALIZED_Y` → `ؿ U+063F`. **Everything else must enter the review queue.**
The classifier must **never** silently assign `ع` to an unresolved case.

### Required corpus audit — all 3,082 occurrences

Claude's preliminary read-only scan of live `app/content.json` found: 3,082 apostrophes total; 254
apostrophe-before-`y`; 2,828 others; sampling of 232 distinct forms suggested paired quotation
(`'ɗaya'`, `'biyu'`, `'babba'` inside `audioScript` narration) dominates the non-`y` set, with genuine
glottal stops (`murabba'i`) comparatively rare. **Independently reproduce these numbers and report whether
Claude's counts were correct**, including your exact method.

Then produce counts broken down by: apostrophe code point · field type · module · surrounding characters ·
inferred category · confidence · **whether the field actually reaches the current live converter** ·
**whether the current engine would alter it** · whether paired opening/closing punctuation is detectable.

Those two call-path questions matter: Claude's standard currently states the blanket apostrophe→`ع` rule
is a *potential* corruption class of *up to* 2,828 occurrences precisely because occurrence-counting alone
does not prove each one is passed through the converter and emitted as `ع`. **This slice is where that
gets determined.** Trace the actual call path in `app/app.js` (read-only) from content field → render →
`romanToAjami()` and report which field types genuinely reach it.

**Do not classify quoted forms by regex alone.** Handle nesting, unmatched quotes, contractions, word
boundaries, adjacent punctuation. Retain representative examples for every category.
