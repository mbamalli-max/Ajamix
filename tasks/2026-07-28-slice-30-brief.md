## Context

Read `tasks/2026-07-28-slice-29-brief.md` and `tasks/2026-07-28-slice-29-report.md` first for the full
background. Summary of the three findings, all independently re-verified before this brief was written:

1. **Orphaned legacy cache rows.** The pre-`a815245` downloader cached formal-track audio under the
   module's single legacy `module.audioFile` key (e.g. `audio/n1-maths-01.mp3`). Post-fix,
   `getAudioUrlsForModule()` returns only the per-segment paths (`audio/n1-maths-01-01.mp3` etc.), so
   `deleteAudioForCompletedModules()` can never reach a legacy row, and no other sweep exists (the only
   `store.clear()` is in `putAllRecords()`, which covers modules/activities/glossary, not `audioCache`).
   Legacy rows are therefore permanently orphaned in IndexedDB.
2. **Cleanup over-reports success.** In `deleteAudioForCompletedModules()` (~app.js:8409), `deletedBytes`
   and the returned `count` are both computed from `recordsToDelete` **before** the delete loop runs, and
   each `deleteRecord` swallows its error with `.catch(function () { return null; })`. A failed deletion
   is still reported to the user as deleted. (Verified pre-existing — byte-identical in `a815245^` — not
   introduced by the offline-download fix, but in scope to fix now.)
3. **Segments-length divergence.** `getAudioUrlsForModule()` (~app.js:6920) treats *any* non-empty
   `segments` array as segmented, while `hasFormalSegments()` (app.js:3857) requires exactly
   `segments.length === 3`. A hypothetical 2-segment formal module would download 2 segment URLs but play
   back through the legacy single-file path. Currently foreclosed by `validate-content.mjs:141` (hard-
   requires exactly 3), so this is defense-in-depth, not a live bug.

## Fix 1 — targeted legacy-key cleanup (NOT a blanket orphan sweep)

**Do not implement a general "delete any audioCache row not in the current URL set" sweep.** That was
considered and rejected: caregiver activities carry their own `activity.audioFile` (see app.js:4233) which
`getAudioUrlsForModule()` does not enumerate (it iterates `state.modules` only). Activity audio happens not
to be cached today, so a blanket sweep would be safe only by accident and would silently delete activity
audio the moment that changes. Implement the narrow, provably-safe version instead:

In `prepareDownloadSession()` (~app.js:8060), which **already** calls `getAllRecords("audioCache")` — reuse
that same `cachedAudio` array, do not add another read. After it is fetched, and before the existing
`cachedMap` is built (or after, your choice, as long as `cachedMap` reflects the post-cleanup state):

- Build the set of legacy keys to purge: for every module in `state.modules` where
  `hasFormalSegments(module)` is true AND `module.audioFile` is a non-empty string, that `module.audioFile`
  value is a legacy key.
- For each `cachedAudio` record whose `record.url` is in that set, `await deleteRecord("audioCache",
  record.url)`. Swallowing errors here is acceptable (best-effort cleanup) **but** log nothing to the user
  and do not let a failure reject `prepareDownloadSession`.
- Exclude the purged records from `cachedMap` so the download session doesn't treat a just-deleted row as
  a completed item.

This is idempotent: after the first run no legacy rows remain, and it is a no-op on a clean install. It can
only ever delete a key that is (a) a formal module's legacy `audioFile` and (b) belongs to a module that now
has exactly 3 segments — never an activity, never a vocational lesson, never a current segment path.

## Fix 2 — count only actual deletions

Rework `deleteAudioForCompletedModules()` so the returned `count` and `bytes` reflect deletions that
actually succeeded:

- Build a url→record map from the `cachedAudio` it already fetches, so each url's `sizeBytes` is available.
- In the delete loop, only count a url and add its bytes when its `deleteRecord` call actually resolves.
  A rejected `deleteRecord` must not contribute to either total.
- Keep the existing behaviour of not throwing out of the function on a single failed delete — it should
  still attempt every url and return partial totals.
- Preserve the existing size-derivation expression exactly:
  `Number(record.sizeBytes || (record.blob ? record.blob.size : 0) || 0)`.
- Keep the existing trailing `await prepareDownloadSession(true); await refreshStorageEstimate();` calls and
  the `{ count, bytes }` return shape unchanged.

## Fix 3 — one source of truth for "is segmented"

In `getAudioUrlsForModule()`, replace the ad-hoc `Array.isArray(module.segments) && module.segments.length`
test with a call to the existing `hasFormalSegments(module)` so download and playback agree on exactly what
counts as segmented. (Both are function declarations in the same IIFE scope, so hoisting makes the
call-before-definition ordering fine — verify this rather than assuming.)

Guard against returning an empty array and thereby losing the legacy fallback: if `hasFormalSegments()` is
true but filtering the segments for non-empty `audioFile` strings yields **zero** urls, fall through to the
legacy `module.audioFile ? [module.audioFile] : []` return rather than returning `[]`. (The validator makes
this unreachable today; it is a safety net, and its presence must not change behaviour for any current
module.)

Leave the vocational branch exactly as it is.
