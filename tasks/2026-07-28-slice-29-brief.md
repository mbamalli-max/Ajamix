## Context

Commit `a815245` (already made, do not amend or reference for editing) changed how formal-track audio
modules resolve their offline-downloadable URLs. Background: `app/content.json` formal modules (v3.0,
`track !== "vocational"`) each carry a `segments` array of exactly 3 objects, each with its own
`audioFile` (e.g. `audio/n1-maths-01-01.mp3`, `-02.mp3`, `-03.mp3`). The in-app segmented player
(functions `loadFormalSegmentAudio`, `resolveAudioSourceForPath`, `getFormalSegmentAudioFile` in
`app/app.js`) looks up cached audio in IndexedDB's `audioCache` object store keyed by exactly that
per-segment `audioFile` string. Before this commit, the offline-download feature's
`getAudioUrlsForModule()` still resolved every formal module to its old, single, legacy
`module.audioFile` field (e.g. `audio/n1-maths-01.mp3` — no `-01/-02/-03` suffix) — a URL the segmented
player never looks up. So "download for offline" was caching audio under a key the player would never
find at playback time.

The claimed fix: `getAudioUrlsForModule()` now returns `module.segments[].audioFile` (all of them, in
order) for any formal module that has a non-empty `segments` array, falling back to the legacy single
`module.audioFile` only when a module has no `segments` (author's claim: none currently lack them — all
359 formal modules have `segments`). `getAudioEntriesForGradeBand()`'s per-item `moduleId` labelling was
also changed: previously only vocational multi-lesson modules got a `-01/-02/...` suffix on `moduleId`;
now any module yielding more than one URL gets the suffix, so the fix doesn't create 3 identically-
labelled download-list entries per formal module.
