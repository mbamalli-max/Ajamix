## Steps

1. **Create `.gitattributes`** at the repo root (it does not currently exist — verify) declaring LFS
   tracking for the image path only:
   ```
   app/images/**/*.png filter=lfs diff=lfs merge=lfs -text
   ```
   Use `git lfs track "app/images/**/*.png"` to generate it rather than hand-writing, then confirm the
   resulting file content. Do not add tracking rules for any other path — audio (`*.mp3`) is gitignored
   and must NOT be added to LFS.

2. **Run the history rewrite**, limited to the unpushed range:
   ```
   git lfs migrate import --include="app/images/**/*.png" --include-ref=refs/heads/main --above=1b
   ```
   Consult `git lfs migrate import --help` on the installed binary and adjust flags if this invocation is
   wrong for 3.7.1 — **verify the flags against the actual binary before running**, do not trust this
   brief's exact syntax (a prior slice in this project was burned by an unverified flag). The essential
   requirement is: only `refs/heads/main` is rewritten, only `app/images/**/*.png` is converted, and
   `8539a75` and its ancestors are left untouched.
   If `--include-ref` alone would still walk past `8539a75`, that is expected — `8539a75` has no images so
   its tree is unaffected in content — but you must still **verify afterwards** (step 4) that `8539a75`'s
   own SHA is unchanged and still an ancestor of the rewritten `main`.

3. **Ensure `.gitattributes` is committed** as part of the rewritten history (or as an additional commit
   on top if the migrate tool doesn't include it) so that future adds are tracked automatically.

## Verification you MUST perform and report (this is the important part)

4. **History integrity:**
   - `git rev-parse 8539a75` still resolves and is unchanged.
   - `git merge-base --is-ancestor 8539a75 main` succeeds (still a fast-forward from the remote).
   - `git log --oneline 8539a75..main` still shows exactly **3** commits, with the same commit *messages*
     in the same order (SHAs WILL differ — that is expected and correct).
   - `backup-pre-lfs` still points at `0ff36fc0a0fc7ff0ab35c94a18f69cddbb4ede1c`.

5. **Content integrity — the critical check.** Prove no image bytes changed. For every one of the 359
   files under `app/images/` in the rewritten `main` tip, compare its **actual content hash** against the
   same path in `backup-pre-lfs`. Because the LFS version stores a pointer in git, you must compare
   *materialized file content*, not blob SHAs. Suggested approach: check out / smudge both states (or use
   `git lfs pointer`/`git cat-file` plus the LFS object store) and compare SHA-256 per file. Report the
   exact method you used and the result. **Any mismatch is a hard stop — report it, do not attempt to
   "fix" it.**

6. **LFS wiring:**
   - `git lfs ls-files | wc -l` returns 359.
   - Spot-check that `git cat-file -p main:app/images/n1-maths-01.png` is now an LFS *pointer* (small text
     starting `version https://git-lfs.github.com/spec/v1`), not binary PNG data.
   - Confirm the working-tree file `app/images/n1-maths-01.png` is still a real, valid PNG of the original
     size (i.e. the smudge filter works).

7. **Repo size:** report `git count-objects -vH` before/after and the size of the pending push
   (`git rev-list --objects 8539a75..main | ...`) so we can confirm the non-LFS pack is now small.

8. **App still valid:** `node app/tools/validate-content.mjs` and
