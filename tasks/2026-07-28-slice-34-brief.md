## Context — read this before starting

Ajamix already has a live, shipped Latin→Ajami transliteration feature. This is **not** a greenfield
build. Claude has already found, by direct inspection, that at least three partially-overlapping and
partially-conflicting sources of Ajami spelling convention exist in this repository right now, none of
which were ever formally declared or independently validated:

1. **`romanToAjami()`** — a phonological rule engine, ~180 lines, defined in `app/app.js` (search for
   `function romanToAjami`) and duplicated near-verbatim in `app/tools/check-ajami-output.mjs`. It is
   **live in production** on `main`: the app's `state.settings.scriptMode` toggle ("latin"/"ajami"), set
   during onboarding and in settings, switches every bilingual field's rendering between `pair.ha` and
   `pair.ajami` — and whenever a reviewed `pair.ajami`/`titleAjami`/`textExplanationAjami` value is absent,
   the app calls `romanToAjami()` live to generate one on the fly.
2. **`docs/ajami-alphabet-guide.md`** — a prose alphabet reference. It partially agrees with the live
   engine (g→غ, ts→ڟ, ɓ→ٻ) but is internally self-contradictory on ƙ (states ق in one table, ڪ in
   another), never commits to an exact codepoint for ɗ (says only "د with dot below" in prose), and does
   not address ƴ, or any f/n contextual variants, at all.
3. **Development fixtures Muhammad supplied directly in chat** (NOT yet in the repo as a file — Claude
   will add them separately as `tasks/2026-07-28-ajami-dev-fixtures.md`, treat as reference input only),
   explicitly marked non-authoritative. These disagree with the live engine on ɓ, ɗ, ƙ, ƴ, f, and a
   contextual n-variant, while agreeing on ts, sh, g, and apostrophe→ain.

None of this is settled. `HAUSA_AJAMI_ORTHOGRAPHY_STANDARD.md` does not exist anywhere in the repo
(confirmed by `find`). Your job is to establish the facts needed to resolve it — **not** to pick a winner
between these sources, and **not** to write any conversion code yet.
